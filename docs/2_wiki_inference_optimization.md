# 1. 베이스라인·후보 모델 비교

> [!NOTE]
> 원래 "기존 모델 추론 성능 지표"는 우리 서비스를 직접 측정해서 내야 하지만, 아직 엔드포인트 구현이 없어 측정할 대상이 없습니다. 대신 **현재 쓰고 있는 Gemini(베이스라인)와 로컬 전환 후보 모델들을 같은 표에 놓고 비교**하는 것으로 대체합니다. 아래 값은 전부 팀 조사·실측 후 채웁니다.

### 1-1) 대상 엔드포인트

| /v1/analyze-video | 영상 저장 시 1회 | 멀티모달(영상+오디오) 이해 필요 | 대상 아님 — 로컬 모델로 대체 시 정확도 손실 큼 |
| /v1/verify-place | 영상 저장 시 1회 | 웹검색 그라운딩 필요 | 대상 아님 — 자체 검색 인프라까지 구축해야 해 이득 없음 |

> `*` 표시된 값은 우리가 직접 측정한 것이 아니라 **각 모델의 공개 벤치마크 문서에 보고된 수치**입니다. 측정 환경(GPU 종류·배치 크기·입력 길이·양자화 여부)이 우리 조건과 다르므로, 모델 간 절대 비교가 아니라 **대략적인 규모 파악용**으로만 사용합니다. 실제 판단은 위 자체 평가 결과를 기준으로 합니다.

**각 항목을 보는 이유**
- **파라미터 수 / 요구 GPU 메모리** — 보유 가능한 GPU에 올라가는지가 로컬 전환 가능 여부를 결정
- **권장 GPU VRAM** — 요구 메모리는 "겨우 올라가는" 하한이고, 권장값은 동시 요청 처리와 KV 캐시 여유까지 감안한 실사용 기준. 인스턴스 사양(=고정비)을 정하는 근거가 됨
- **지연 시간 / 처리량** — 전환으로 얻는 성능 이득을 판단하는 핵심 지표
- **출력 처리 속도** — 지연 시간을 만들어내는 원인. 우리 후보 엔드포인트는 출력이 JSON이라 길이가 길고, `recommend-courses`의 적합도 판단은 후보 수에 비례해 출력이 늘어나므로 이 값이 곧 지연으로 이어짐
- **호출당 비용** — 로컬은 호출당 과금이 아니므로, GPU 고정비를 예상 호출량으로 나눈 환산값으로 비교 ([4-3](#4-3-기대-비용과-손익분기-호출량) 참고)

**실측 필요 항목**
- 위 병목 각각이 실제로 지연에 얼마나 기여하는지 (예: 후보 수를 5→40으로 늘렸을 때 지연 증가폭)

# 3. 최적화 기법 계획

### 3-1) 최적화 대상 선정 근거

`extract`와 `recommend-courses`는 모두 **입력·출력이 텍스트이고 정해진 JSON 스키마로 구조화된 출력**을 낸다는 공통점이 있어, 로컬 모델로 대체할 수 있는지 검증할 가치가 있습니다.

다만 둘의 성격은 서로 다릅니다.

- `extract` — 대화 턴마다 호출되는 고빈도 API. **지연 시간과 누적 비용 개선 효과가 가장 크고**, 슬롯 추출이라는 단순 작업이라 품질 리스크도 낮습니다.
- `recommend-courses` — 저빈도지만 **판단 품질(적합도 평가, 코스 제목의 자연스러움)이 사용자 경험에 직결**됩니다. 내부 LLM 호출이 적합도 판단과 코스 조합 2회로 나뉘어 있어, 둘을 따로 전환·평가할 수 있습니다. 속도·비용만 보고 전환하면 안 되고 출력 품질을 Gemini 대비 비교 검증해야 합니다. (→ [3-5](#3-5-품질-검증-방법))

### 3-2) 학습 데이터 확보 및 지식 증류 (Knowledge Distillation)
- 로컬 모델을 태스크에 맞게 파인튜닝하려면 `입력 → 출력` 쌍 데이터가 필요합니다. **현재는 서비스 운영 전이라 축적된 호출 로그가 없으므로**, 데이터를 먼저 확보해야 합니다.
- 확보 방법: ① Gemini API 호출 결과를 저장하는 로깅을 먼저 붙이고 개발·테스트 기간 동안 축적, ② 부족하면 다양한 발화·후보 조합을 만들어 Gemini로 정답 데이터를 의도적으로 생성.
- 이렇게 모은 Gemini(teacher) 출력을 정답으로 삼아 로컬 모델(student)을 파인튜닝합니다. 별도 사람 라벨링이 필요 없다는 점이 이 방식의 장점입니다.

### 3-3) 양자화 (Quantization)
- INT8/INT4(AWQ 또는 GPTQ) 양자화로 모델 크기와 연산량, GPU 메모리 점유를 줄입니다.
- 세 태스크 모두 자유 생성이 아니라 정해진 스키마 안에서의 구조화 출력이라, 양자화로 인한 품질 손실 영향이 상대적으로 적습니다.

### 3-4) 배치 처리 및 하드웨어 가속
- vLLM 등으로 동시 요청을 dynamic batching 처리합니다. 자체 서빙이므로 외부 API와 달리 배치 스케줄링을 직접 제어할 수 있습니다. (2번의 "배치 불가" 병목 해소)
- GPU 위에서 TensorRT-LLM 또는 vLLM의 PagedAttention을 활용해 처리량을 높입니다.

### 3-5) 품질 검증 방법
- `extract` — 슬롯 추출은 정답이 비교적 명확한 태스크라, 동일 입력에 대한 Gemini 결과와 로컬 모델 결과를 **슬롯 값 단위 exact match**로 비교해 정확도를 측정합니다.
- `recommend-courses` — 점수·코스 제목처럼 정답이 하나로 정해지지 않으므로, 동일 입력에 대한 두 결과를 나란히 놓고 **팀 내 블라인드 비교 평가**(어느 쪽이 더 적절한지)를 수행합니다.
- 품질 저하가 허용 기준 이내인 엔드포인트만 실제 전환 대상으로 채택하고, 기준을 넘으면 API를 유지합니다.

### 3-6) 장애 대응(폴백) 전략
- 로컬 모델 서버가 응답하지 않거나 타임아웃되면, 해당 요청을 **Gemini API 호출로 자동 폴백**합니다.
- 두 경로의 요청·응답 스키마가 `docs/wiki_api_design.md`로 동일하게 고정되어 있으므로, 호출하는 백엔드 코드를 바꾸지 않고 내부에서 경로만 전환할 수 있습니다.

### 3-7) 로컬 전환 시 감수해야 하는 부담

| 항목 | 내용 |
| --- | --- |
| GPU 인프라 고정비 | API는 호출한 만큼만 과금되지만, 로컬 서빙은 요청이 없어도 GPU 서버 비용이 계속 발생함. **호출량이 손익분기점을 넘어야 비용 이점이 생김** |
| 동시 처리 한계 | GPU 메모리 크기가 동시 처리 가능한 요청 수의 상한이 됨. API는 이 제약이 없음 |
| 콜드 스타트 | 모델 로딩에 시간이 걸리므로, 상시 기동 상태를 유지해야 함(= 고정비 증가 요인) |
| 운영 부담 | 모델 버전 관리·장애 대응·스케일링을 직접 해야 함 |

### 3-8) 단계별 실행 계획

| 단계  | 작업                             | 채워지는 항목            |
| --- | ------------------------------ | ------------------ |

### 비고

- 실제 전환 여부는 성능·비용·품질 세 지표를 함께 보고 개별 결정합니다 — 일괄 전환이 아니라, 세 조건을 모두 만족하는 것만 선별 적용합니다. `recommend-courses`는 내부 LLM 호출 2회를 따로 판단할 수 있습니다.
