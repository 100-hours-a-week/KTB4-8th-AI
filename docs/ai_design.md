# AI 설계

## 단계 1: 모델 API 설계

> **Why:** AI 모델을 서비스에 통합하려면 외부 또는 다른 모듈에서 모델 기능을 안정적으로 호출할 수 있는 인터페이스가 필요하다. 잘 정의된 API는 서비스 구성 요소 간 경계를 명확히 하고, 모델을 다른 부분과 분리(decouple)하여 개발 및 배포를 용이하게 한다. 
> 만약 API가 부실하면 각 팀의 서비스 코드에 모델 호출 로직이 뒤섞여 유지보수가 어렵고, 다른 서비스나 클라이언트가 모델 기능을 활용하기도 힘들어진다. 
> 따라서 표준화된 API를 먼저 설계하는 것은 향후 확장성과 협업을 위해 필수적이다.
> 
> **설계 과제:** 팀의 서비스 요구사항에 맞는 머신러닝 모델 API를 설계하고 구현하라. 
> 예를 들어 RESTful API를 이용하여 **모델 예측 기능을 호출하기 위한 엔드포인트**를 정의하고, 입력 데이터 형식과 출력 결과 구조를 명확히 문서화한다.
> 필요한 경우 오류 처리 방안(예: 잘못된 입력에 대한 대응)과 인증/권한 관리도 고려하라. 
> API 설계 시 **본 모델 API가 팀의 기존 서비스 아키텍처와 어떻게 연계되는지**를 설명하여, 해당 API를 통해 서비스의 어떤 기능이 강화되거나 구현되는지 논리적으로 드러내라. 
> 
> **제출 항목:**
> 
> - 설계한 API의 엔드포인트 목록과 각 엔드포인트의 기능 설명 (예: `/predict`: 입력을 받아 모델 추론 결과 반환).
> - API의 입력(JSON 혹은 Proto 메시지 등)과 출력 형식에 대한 명세서 (스키마, 예시 포함).
> - 해당 API가 서비스 전체 구조에서 차지하는 역할과 연동 관계에 대한 설명 (다이어그램이 있다면 첨부).
> - API 호출 예시와 예시 응답 (테스트를 통해 확인한 결과).



## 단계 2: 모델 추론 성능 최적화

> **Why:** 초기 통합된 모델은 기능을 만족하더라도, 추론(latency) 지연이나 과도한 자원 소모로 실제 서비스에 부담을 줄 수 있다.
> **모델 추론 최적화**는 사용자가 체감하는 응답 시간을 줄이고 인프라 비용을 낮추며, 더 많은 요청을 감당할 수 있게 해준다.
> 예를 들어 최적화 없이 대형 모델을 호출하면 한 요청에 수 초 이상 걸릴 수 있지만, 적절한 최적화 기법을 적용하면 지연 시간을 크게 단축할 수 있다.
> 또한 서비스 맥락에 맞는 최적화를 하지 않으면, 불필요한 계산 낭비나 성능 병목이 발생해 확장성이 저해된다.
> 따라서 팀별 서비스 상황에 맞춘 추론 최적화는 안정적이고 효율적인 AI 서비스 운영의 핵심이다.
> 
> **설계 과제:** 현재 사용 중인 AI 모델의 추론 성능을 분석하고, **서비스 요구사항에 부합하는 최적화 기법을 적용**하라. 먼저, 모델 추론 단계의 프로파일링을 수행하여 주요 **병목 요소**(예: 모델 크기로 인한 CPU/GPU 부하, 불필요한 연산, I/O 지연 등)를 식별하라.
> 그런 다음, 문제에 적합한 최적화 방안을 선택하여 적용하라.
> 예시 방안으로는 **모델 경량화(quantization, knowledge distillation)**, **배치 처리 및 캐싱**을 통한 처리량 향상, **하드웨어 가속(CUDA/TensorRT 등)** 활용, 또는 **사전 연산 결과 캐싱** 등이 있다.
> 선택한 기법은 반드시 팀 서비스의 특성과 트래픽 패턴에 어울리는 것이어야 하며, **왜 해당 최적화가 자기 서비스에 효과적인지 서비스 맥락에서 설득력 있게 설명**하라.
> 최적화 전후의 성능(추론 속도, 응답 시간, 자원 사용량 등)을 측정하여 개선 결과를 검증하고, 그 수치를 근거로 최적화의 효용성을 뒷받침하라.
> 
> **제출 항목:**
> 
> - 기존 모델 추론의 성능 지표  (동일한 조건에서의 지연 시간 감소, 처리량 향상 등 개선된 수치)..
> - 식별된 성능 병목 요소와 그 원인에 대한 분석 내용.
> - 적용할 최적화 기법의 구체적 계획  (동일한 조건에서의 지연 시간 감소, 처리량 향상 등 개선된 수치)..
> - 최적화 적용 후의 기대 성능 지표 (동일한 조건에서의 지연 시간 감소, 처리량 향상 등 개선된 수치).


## 단계 3: 서비스 아키텍처 모듈화

> **Why:** 모델을 서비스에 통합하는 과정에서 **아키텍처의 모듈화**를 달성하면 개발 효율과 시스템 유지보수성이 크게 향상된다.
> 모듈화된 구조에서는 모델 관련 기능이 독립된 컴포넌트나 마이크로서비스로 분리되어, 다른 기능과 결합도를 낮춘다.
> 이렇게 하면 모델을 교체하거나 업데이트할 때 서비스 전체를 수정할 필요가 없고, 여러 팀원이 병렬로 작업하기에도 용이하다.
> 만약 모델 로직이 프론트엔드나 비즈니스 로직과 뒤섞여 있다면, 작은 변경도 전체 서비스에 영향을 미치고 오류 발생 시 원인 추적이 어려워진다.
> 그러므로 서비스 요구사항을 충족하면서도 변화에 유연한 구조를 위해 모델 서빙 부분을 적절히 분리·모듈화해야 한다.
> 
> **설계 과제:** 팀 서비스의 전체 시스템 구조를 검토하고, **AI 모델 관련 기능을 별도의 모듈이나 서비스로 분리**하는 리팩토링/설계를 수행하라. 예를 들어 현재 단일 애플리케이션에 모델 추론 코드가 섞여 있다면, 이를 **모델 서빙 전용 모듈** 혹은 **독립된 마이크로서비스**로 분리하는 것을 고려하라.
> 모듈 간 인터페이스(예: API 호출, 메시지 큐, 함수 호출 등)를 정의하여 데이터 입력, 모델 추론, 결과 후처리의 흐름이 명확히 분리되도록 설계한다.
> 이 때 팀의 서비**스 도메인에 맞게 어떤 경계(boundary)로 모듈을 나눌지 결정해야 하며, 선정한 모듈화 방식이 서비스 구조에 적합한 이유를 설계 관점에서 명시하라 (예: "실시간 추론 부분을 마이크로서비스화하여 다른 기능 배포와 분리함으로써 안정성을 높였다"). 각 모듈은 독립적으**로 개발/배포/스케일링이 가능해야 하므로, 이에 대한 고려사항(예: 데이터 교환 방식, 호환성)도 함께 정리한다.
> 
> **제출 항목:**
> 
> - 모듈화 적용 후 새롭게 설계된 서비스 아키텍처 다이어그램 (모델 모듈/서비스와 다른 구성 요소를 명확히 표시).
> - 각 모듈의 책임(domain)과 기능에 대한 설명 (어떤 기능을 담당하며 왜 해당 모듈로 분리했는지).
> - 모듈 간 인터페이스 설계 내용 (API 명세, 데이터 포맷, 통신 방식 등).
> - 모듈화로 기대되는 효과와 장점에 대한 정리 (팀 서비스의 개발 및 운영 측면에서의 이점).
> - **모듈화된 설계가 팀의 서비스 시나리오에 부합함을 설명하는 근거** (예: 변경 요구사항 발생 시 영향 범위가 줄어드는 모습 등 구체 사례).

## **단계 4: 멀티스텝 AI/파이프라인 구현 검토 (모델 유형별)**

Why: 복잡한 AI 응용에서 여러 모델이나 모듈을 순차적으로 호출하는 파이프라인이 필요할 수 있다. 텍스트 기반 서비스라면 LangChain을 활용해 질의·검색·응답을 체인으로 구성할 수 있다. 반면 비전이나 음성 서비스에서는 객체 탐지→특징 추출→분류 같은 전처리·후처리 단계가 이어지며, 이 흐름을 체계적으로 설계해야 한다. 예를 들어 Vision 파이프라인에서는 여러 기초 모델을 프롬프트 기반으로 연결하여 영상 이해를 수행하고, 오디오 파이프라인에서는 잡음 제거→음성 인식/VAD/화자 분리→의미 분석 단계를 조합할 수 있다. 이미지/영상 생성 서비스는 텍스트 프롬프트 처리, 참고 이미지/영상 검색, 생성 모델 호출, 후처리(예: 프레임 정합, 압축) 등의 여러 단계를 거칠 수 있다. 이러한 복잡성이 모든 서비스에 필요한 것은 아니므로, 자신의 서비스에 멀티스텝 파이프라인이 유의미한지 검토하여 선택한다.

설계 과제:

1. LLM 서비스: 기존처럼 LangChain이나 유사 프레임워크를 사용해 질의 처리 흐름을 설계한다.
2. 비전 서비스: 객체 검출, 특징 추출, 분류, 자세추정 등으로 구성된 파이프라인을 설계하고, 각 모듈 간 인터페이스와 병목을 식별한다.
3. 음성 서비스: 음성 전처리, 음성 인식(또는 임베딩 추출), 의미 분석 단계로 구성된 파이프라인을 정의한다. 필요한 경우 TTS, STT, VAD 모듈을 포함한다.
4. 이미지/영상 생성 서비스: 생성 과정에서 필요한 여러 단계를 체계화한다. 예를 들어, Text-to-Image 생성에서 참고 이미지/텍스트를 검색한 뒤 이미지 생성 모델을 호출하여 고해상도 이미지를 생성하고, 후처리로 스타일 변환이나 압축을 수행한다. Text-to-Video 생성의 경우, 프롬프트 분석, 레퍼런스 영상 검색, 생성 모델 호출, 프레임 일관성 후처리 등을 설계한다.
5. 기타 모델: 필요에 따라 여러 알고리즘이나 도구를 조합해야 한다면, 해당 흐름을 명확히 정의한다.

제출 항목:

- 설계한 멀티스텝 체인/파이프라인의 다이어그램(각 단계와 역할 설명).
- 사용한 모델·도구·프레임워크 목록, 선택 이유와 기대 효과.
- 구현 코드의 일부 또는 의사코드(프롬프트 구성, 모듈 호출 함수 등).
- 멀티스텝 구조 도입으로 기대되는 이점과 서비스 요구와의 관련성, 혹은 멀티스텝이 불필요하다고 판단한 이유.

## **단계 5: 데이터/컨텍스트 보강 설계 (RAG, RA-IS, VRAG 등)**

Why: 외부 데이터나 레퍼런스를 검색하여 모델 입력을 보강하면, 훈련 데이터에 없는 정보나 최신 지식을 활용할 수 있다. 전통적인 RAG는 LLM이 텍스트 지식 베이스에서 정보를 검색해 응답 정확도를 높인다. Visual RAG는 이미지·텍스트 쌍을 검색하여 비전 모델의 이해를 향상시키고, Re-Imagen 같은 Retrieval-Augmented Image Generator는 드문 객체의 이미지를 생성하기 위해 외부 데이터베이스에서 관련 이미지/텍스트를 검색해 고품질 이미지를 생성한다. Retrieval-Augmented Video Generation은 영상 생성 시 외부 영상 예제를 검색해 모션 실감도를 개선한다. SpeechRAG는 텍스트 쿼리와 음성을 공통 임베딩 공간에 매핑해 ASR 없이도 음성 데이터를 검색하고 질문에 답한다.

**설계 과제:**

1. 텍스트/LLM 서비스: 기존 RAG처럼 텍스트 지식 베이스 구축·검색·증강 구조를 설계한다.
2. 비전 서비스: Visual RAG 또는 유사한 기술을 적용한다. 이미지/영상 DB를 구축하고, 사용자 질의(텍스트/이미지)에 맞춰 관련 시각 정보를 검색하여 모델 입력을 증강한다.
3. 음성 서비스: Speech RAG를 고려한다. 음성과 텍스트를 같은 임베딩 공간에 맵핑해 직접 음성 데이터를 검색하여 질문에 응답하거나 음성 생성 모델에 연결한다.
4. 이미지/영상 생성 서비스: Retrieval-Augmented Image Synthesis (RA‑IS) 또는 Retrieval-Augmented Video Generation을 설계한다. 텍스트 프롬프트에 대해 관련 이미지/영상 예제를 검색하여 생성 모델에 조건으로 사용한다. Re-Imagen과 RDM에서처럼, 검색된 이미지·텍스트 쌍을 입력에 포함해 드문 객체나 특정 스타일의 이미지를 더 정확하게 생성할 수 있다. 영상 생성의 경우, 외부 영상에서 모션 예제를 가져와, 텍스트-to-비디오 모델의 움직임을 현실감 있게 유도한다.
5. 기타 모델: 필요에 따라 검색 기반 컨텍스트 보강을 설계하거나, 주기적 재학습·파인튜닝 전략을 제시한다.

**제출 항목:**

- 전체 데이터 흐름도(입력 → 검색 → 증강 → 모델 응답/생성 결과).
- 사용 데이터/지식 소스 설명과 선택 이유(예: 이미지/영상 DB, 음성 데이터베이스, 텍스트 문서 등).
- 검색·임베딩·인덱싱 구현 내용과 모델 통합 방법(프롬프트 또는 입력 포맷).
- 컨텍스트 보강 도입 전후 예상 효과와 검증 계획, 혹은 도입이 불필요한 경우 그 이유.

## **단계 6: 표준화된 도구 통합 및 외부 API 활용 설계 (MCP 등)**

Why: MCP는 AI 모델과 외부 도구·데이터 소스를 표준화된 방식으로 연결하는 프로토콜로, 다양한 도구를 쉽게 통합할 수 있게 한다. 특히 이미지/영상 생성, 고도화된 비전·음성 파이프라인은 높은 연산 요구를 가지므로, GPU 자원 부족 시 상용 API(예: OpenAI, Gemini 등)를 활용해야 할 수 있다. 이런 API를 호출할 때도 표준화된 인터페이스와 권한 관리가 중요하다. 또한 API 비용, 응답 지연, 서비스 안정성 등을 고려해야 한다.

설계 과제:

1. 외부 시스템/도구/서비스와 상호작용해야 하는 시나리오를 파악한다. 이미지 생성 API 호출, 영상 분석 API, 음성 합성 API, 데이터베이스 조회 등.
2. MCP나 비슷한 표준 프로토콜을 사용하여 이러한 도구들을 연결할지 결정한다. MCP를 도입한다면, MCP 서버·클라이언트 구조, 툴 정의, 권한 모델, 상용 API 호출을 포함한 다이어그램을 설계한다.
3. 상용 API를 사용할 경우, 자체 모델 구축 vs. API 사용의 장단점을 분석한다. GPU 인프라 비용과 대비하여 API 사용 비용(예: 이미지 생성 API의 단가 ￼), 호출 제한, 지연 시간, 데이터 보안 등을 고려하고, API 응답을 캐싱하거나 Fallback 전략(예: 사전 생성한 콘텐츠 활용)도 설계한다.
4. MCP를 도입하지 않는 경우, REST/gRPC 등의 기존 인터페이스로 모듈을 분리하고, 상용 API 호출을 관리하는 모듈을 설계한다. 모든 외부 호출은 예외 처리, 재시도, 속도 제한 제어를 포함해야 한다.
5. 장기적으로 새로운 도구나 API를 추가할 때 확장성을 어떻게 보장할 것인지 계획한다.

제출 항목:

- MCP(또는 대체 프로토콜)를 포함한 도구·서비스 통합 다이어그램, 각 도구/서비스의 역할과 호출 목적.
- 상용 API 사용 시, 선택한 API 목록과 사용 이유, 비용·성능·제약 조건 분석, 그리고 내부 모듈화 계획.
- MCP를 도입하지 않는 경우에는 API 호출을 포함한 현재 인터페이스 설계와 확장 계획.
- 선택한 통합 방법이 팀 서비스의 확장성·유지보수성·비용 효율성에 미치는 영향에 대한 설명.

## **단계 7: 서비스 인프라 확장성과 모니터링 설계**

Why: 개발 환경에서 성공적으로 동작한 모델 기반 서비스라도, 실제 사용자 트래픽을 처리하려면 확장성과 안정성을 갖춘 인프라 설계가 필요하다. 확장성은 서비스가 증가하는 요청 부하를 감당할 수 있게 하는 능력으로, 이를 위해 컨테이너화, 오토스케일링, 부하 분산(load balancing) 등의 기술을 활용한다. 또한 시스템 안정성을 위해 장애 발생 시 복구 전략과 성능 모니터링 체계를 마련해야 한다. 만약 이러한 인프라 고려 없이 서비스를 운영하면, 소수의 동시 요청에도 응답 지연이나 오류가 발생할 수 있고, 문제 발생 시 원인을 파악하지 못해 장기적인 서비스 운영에 차질을 빚게 된다. 따라서 서비스 운영 단계에서는 배포 환경에서의 구조적인 확장성 확보와 모니터링을 통한 실시간 가시성 확보가 필수적이다.

설계 과제: 팀의 모델 서빙 컴포넌트를 운영 환경에 배포한다는 가정 하에, 높은 트래픽을 처리할 수 있는 인프라 구조와 모니터링 계획을 설계하라. 먼저, 현재 모델 서빙 모듈/서비스를 컨테이너(Docker 등)로 묶거나 패키징하여 일관된 배포 단위로 만든다. 그런 다음, 수평적 스케일링(horizontal scaling)을 고려하여 동일한 모델 서비스 인스턴스를 여러 개 띄우고, 로드밸런서나 API 게이트웨이를 통해 트래픽을 분산시키는 아키텍처를 구상한다. 클라우드 서비스의 오토스케일링 기능이나 쿠버네티스(Kubernetes)를 활용하는 것도 고려한다. 아울러, 모니터링 및 로깅 부분에서는 주요 지표(모델 응답 시간, 오류율, CPU/GPU 사용률 등)를 수집하고 대시보드나 알림으로 확인할 수 있는 체계를 제안한다. 이에는 Prometheus/Grafana 같은 모니터링 스택 활용이나 간단한 로그 수집 및 분석도 포함될 수 있다. 설계 시 팀 서비스의 예상 트래픽 규모와 특성을 반영하여, 왜 해당 수준의 인프라와 모니터링이 필요한지 설명하라. 예를 들어, 실시간 서비스라서 99퍼센타일 응답속도를 모니터링해야 한다든지, 일별 사용자 수에 따라 몇 대의 서버가 필요하다든지 하는 구체적인 고려를 제시한다.

제출 항목:

- 확장성을 고려한 배포 아키텍처 다이어그램 (예: 여러 모델 서비스 인스턴스와 로드밸런서 구성, 오토스케일링 정책 등).
- 사용한 인프라 기술 및 서비스 명세 (Docker, Kubernetes, AWS/GCP 등 클라우드 자원, 혹은 On-premise 환경 설정 등 구체적으로).
- 모니터링 대상 지표 목록과 수집/시각화 방법 (예: 응답 시간, Throughput, 에러 로그 등과 Grafana 대시보드 구성안).
- 간이 부하 테스트 또는 시뮬레이션 결과 (가능하다면)와 그에 따른 시스템 자원 사용량/응답시간 변화 분석.
- 제안한 인프라/모니터링 설계가 팀 서비스의 향후 성장과 안정적 운영에 어떻게 기여하는지에 대한 설명 (예: "사용자 100배 증가 시에도 대응 가능하도록 OOO를 구성하여 서비스 중단 없이 확장 가능").

## **단계 8: 최종 통합 설계 및 회고**

Why: 이제까지의 단계를 통해 개별적으로 추진한 설계와 개선 사항들을 서비스 전체의 통합된 아키텍처로 종합할 필요가 있다. 각각의 단계는 특정 영역의 향상이지만, 최종적으로는 모든 요소가 잘 맞물려 하나의 완성도 높은 시스템을 이뤄야 한다. 또한 각 단계에서 내린 설계상의 결정들이 상호 작용하면서 새로운 고려사항이 생길 수도 있으므로, 이를 조정하고 정리하는 과정이 중요하다. 아울러, 프로젝트 전체를 돌아보며 배운 점이나 한계점을 정리하면 향후 개선 방향을 설정하는 데 도움이 된다. 이 최종 회고 단계에서는 팀의 서비스에 적용된 AI 모델 서빙 아키텍처를 한눈에 볼 수 있도록 정리하고, 설계 의도 대비 실제 결과를 평가하여, 강사나 이해관계자가 보았을 때도 납득할 수 있는 완성도를 갖추었는지 확인한다.

설계 과제: 이전 단계에서 구현한 모든 설계 요소를 통합하여 최종 서비스 아키텍처와 결과물을 정리하라. 팀의 위키에 전체 시스템 구조를 다시 한 번 최신 상태로 다이어그램화하고, 각 구성요소(API, 모델 모듈, 체인/RAG/MCP 적용 부분, 인프라 등)가 어떻게 상호 연동되는지 설명한다. 이 때 각 구성요소를 도입한 이유와 그로 인한 효과를 간결히 정리하여, 단계별 설계의 타당성을 다시 한 번 강조한다 (예: "모델 모듈화로 인해 다른 기능 수정 시 영향을 받지 않고, 독립 배포가 가능해졌다"). 또한 프로젝트 수행 과정에서 얻은 인사이트를 토대로, 현재 아키텍처의 강점과 약점, 추가로 보완해야 할 여지 등을 분석하라. 가능하다면 정량적인 결과(예: 전체 시스템 처리량, 최종 사용자 만족도 향상 등)를 제시하여 성과를 평가한다. 마지막으로, 향후 단계에서 고려할 사항이나 발전시킬 아이디어(예: 모델 추가 개선, 신규 기능 통합 등)를 제안하라. 이를 통해 설계 과제가 실제 서비스 발전으로 이어질 수 있음을 보여주어야 한다.

제출 항목:

- 최종 통합된 서비스 아키텍처 다이어그램 및 설명 (이전에 제안된 설계 요소들이 모두 반영된 그림과 각 요소 설명).
- 단계별 설계 적용 결과 요약표 (각 단계의 주요 변경사항과 그에 따른 성능/품질 향상 요약).
- 현재 완성된 시스템의 성능/품질에 대한 평가 (가능한 경우 정량적 데이터 포함).
- 프로젝트 수행에 대한 회고 및 평가: 무엇을 배웠고 어떤 어려움이 있었는지, 이를 어떻게 해결했거나 해결하지 못했는지.
- 앞으로의 개선 제안 및 계획: 추가 구현하고 싶은 기능이나 필요할 수 있는 최적화, 또는 다음 연구/개발 방향에 대한 제언.
- 전반적인 결론으로서, 현 시점에서 팀의 AI 모델 서빙 아키텍처가 왜 타당하고 적절한지에 대한 종합적인 의견 (전체 설계를 다시 한 번 옹호하는 내용).
